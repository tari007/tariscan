# TariScan POS

TariScan POS is an offline-first retail point-of-sale and inventory management application in development. It is designed for small shops, supermarkets, pharmacies, wholesalers and other retail businesses.

## Technology

- Next.js 15, React 19 and TypeScript
- Tailwind CSS 4 and Lucide icons
- Supabase Authentication and PostgreSQL
- Dexie / IndexedDB for local-first records
- html5-qrcode for camera barcode scanning
- Vercel hosting

## Implemented workflows

- Email/password authentication and business onboarding
- Local product catalogue, inventory quantities and barcode lookup
- POS checkout, discounts, manually recorded payment methods and printable receipts
- Local sales history and full-refund recording with stock restoration
- Customer and supplier directories
- Goods receiving and stock replenishment
- Expense recording and local financial reports
- Staff membership and role assignment
- Database-enforced role permissions for cloud operations
- Automatic audit events for cloud record changes
- Local sync queue for supported data types

## Staff roles

- **Owner:** Full business access and staff administration.
- **Manager:** Sales, refunds, products, inventory, customers, suppliers, purchases, expenses and reports.
- **Supervisor:** Operational access including sales, refunds, inventory, expenses and reports.
- **Cashier:** Product lookup, checkout and customer records. A cashier can sync stock reductions generated by checkout but cannot edit product details or issue refunds.
- **Stock clerk:** Product and inventory maintenance, supplier records and goods receiving.

The database is the enforcement layer for cloud permissions. The offline browser database is not a tamper-proof security boundary. Offline actions are queued locally and are checked against the signed-in account's current permissions when synchronised. Audit events identify the authenticated account that performs the cloud sync. If different staff share one device or queued work is synchronised under a different account, this is not a guaranteed record of the original offline operator.

## Supabase setup

1. Create a Supabase project.
2. Add `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` to your local `.env.local` and Vercel environment variables.
3. Run the SQL migrations in the order listed below.
4. Configure Supabase Authentication site and redirect URLs for your local and deployed domains.
5. Redeploy after adding or changing environment variables.

### Migration order

Run each file once in the Supabase SQL Editor, in numerical order:

1. `202611170001_initial_business_setup.sql`
2. `202611170002_offline_sync_tables.sql`
3. `202611180001_checkout_payment_details.sql`
4. `202611180002_sales_refund_management.sql`
5. `202611180003_customers_suppliers_purchases.sql`
6. `202611180004_expenses.sql`
7. `202611180005_staff_permissions_audit.sql`
8. `202611180006_staff_security_audit_hardening.sql`
9. `202611180007_business_owner_membership_trigger.sql`
10. `202611180008_role_aware_operations_audit.sql`
11. `202611180009_role_aware_write_guards.sql`

The staff migration assumes the earlier business and operational tables already exist. Existing owners are backfilled into the membership table. New business owners are added automatically by a database trigger.

Never expose a Supabase service-role key in browser code or a `NEXT_PUBLIC_` variable. The application uses the Supabase publishable key with Row Level Security. The older anon key variable remains supported for backwards compatibility.

## Run locally

Requirements: Node.js 20.9 or later and npm.

```bash
npm install
npm run dev
```

Open http://localhost:3000.

To create a production build:

```bash
npm run build
npm start
```

## Important limitations

- Local records are stored in the browser's IndexedDB. Clearing browser data or losing the device can remove unsynchronised records.
- Sync is a push queue for supported local records. Full multi-device cloud download, conflict resolution and stock-ledger reconciliation remain future work.
- Mobile browsers may suspend background work. Reopening the app or restoring connectivity is needed to resume sync reliably.
- Offline browser storage does not provide tamper-proof role enforcement. Cloud writes are checked by Supabase RLS when synchronised.
- Cash, bank transfer and card are recorded as payment methods. TariScan does not process payments through a bank or payment gateway.
- Reports are calculated from local records and are management estimates, not statutory financial statements. Historical cost data may be incomplete.
- The audit trail records cloud database changes and the authenticated account performing the sync. It does not yet prove which person performed every offline action.

## Build 12: PWA and local backup

- The app includes a web app manifest and can be installed where the browser supports PWA installation.
- The service worker caches only same-origin static assets and the generic offline fallback. It does not cache authenticated pages, Supabase requests, API responses or business records.
- The offline fallback confirms that a page could not be loaded. It does not make every application route available offline. Previously loaded app code and IndexedDB-backed features still depend on browser cache availability.
- The Backup and Restore screen is available at `/backup`. It exports the current business's local IndexedDB records and sync queue to a JSON file. Restore is restricted to a matching business ID and replaces that business's local records on the current device.
- Backup files contain sensitive customer and business data. Store them securely. Restore does not upload all records to Supabase or download cloud records.
- Sync retries when connectivity returns and when the app becomes visible. Mobile operating systems can suspend background work, so keep the app open during important synchronisation and verify the pending count reaches zero.
- Baseline browser security headers are configured in Next.js. A restrictive Content Security Policy and server-side rate limiting require deployment-specific testing and are not claimed as implemented.


## Build 13: testing and release preparation

- Added Node's built-in test runner for sale quantity aggregation and stock calculation rules. Run with `npm test`.
- Checkout now aggregates repeated cart lines by product before deducting stock. This prevents duplicate lines from deducting less stock than the customer purchased.
- Sync queue replacement is scoped to both business ID and record ID.
- Concurrent sync tasks are isolated per business so one business's active sync does not block another business.
- Backup restore checks business ownership, table record IDs, supported queue entities, queue payload identity and retry metadata before replacing local data.
- The dashboard now displays a notice that its charts, example transactions, stock alerts and headline totals are illustrative placeholders. They are not live records.

### Deployment readiness checklist

1. Configure `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` in Vercel.
2. Run all eleven Supabase migrations in the order listed above.
3. Set Supabase Authentication site URL and redirect allow-list for the production domain.
4. Register the production domain in Vercel and deploy the `main` branch.
5. Sign in as the business owner and verify business setup.
6. Create a test product, record a sale, verify stock reduction, record a refund and verify stock restoration.
7. Test camera scanning on HTTPS and grant camera permission.
8. Test offline checkout, reconnect, and verify the sync queue reaches zero.
9. Export a backup, restore it into a test business with the matching business ID, and verify records.
10. Test staff accounts with separate browser sessions and verify denied operations are rejected by Supabase.
11. Verify PWA installation and offline fallback on supported mobile browsers.
12. Review GitHub Actions and Vercel deployment logs before inviting real businesses.

A green CI build does not verify live Supabase policies, authentication redirects, browser camera permissions, PWA installation on every device, or real multi-device conflict behaviour. These require environment-backed acceptance testing. Do not use production business records for initial testing.


## Build 14: production configuration gate

- Added a configuration-required screen for deployments that have missing, placeholder or malformed Supabase URL/key values.
- Middleware now blocks application routes until valid public Supabase configuration is present, rather than allowing users into an application that cannot authenticate.
- The configuration screen explains which public values belong in Vercel and warns against exposing the Supabase service-role key.
- This gate validates configuration shape only. It does not prove that the Supabase project is reachable, that its migrations have run, or that authentication and RLS are working.

### Production acceptance remains required

Before real business use, complete the deployment checklist above against the actual Supabase and Vercel projects. Confirm authentication, all eleven migrations, owner and staff permissions, offline queue recovery, backup/restore and HTTPS camera access. The current GitHub CI workflow verifies unit tests, TypeScript and a Next.js production build. It does not run browser end-to-end tests or validate live cloud configuration.


## Build 15: authentication redirect hardening

- Added a shared internal-path validator for post-login navigation.
- Login now rejects absolute and protocol-relative external destinations and falls back to the correct dashboard or business setup route.
- Added automated tests for normal internal paths, external URLs, protocol-relative URLs, backslash redirect attempts and invalid values.
- These checks reduce open-redirect risk in the login flow. They do not replace Supabase authentication, RLS, deployment security review or live acceptance testing.
